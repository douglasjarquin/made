=== QA Scenario (Task 9): Sequential queuing under concurrent pushes ===

The real 9-stage pipeline (Tasks 10-19) does not exist yet, so this run
manager is exercised with a fake work function (sleep-then-complete) that
records, via an atomic counter, whether two runs against the same gate-repo
identifier were ever active at the same instant. TestRunManager_SequentialQueuing
submits two runs back to back against the same repo identifier "gate-repo-A"
and asserts:
  1. immediately after both Submit calls, run 2's status is still "queued"
     (not started, not rejected) while run 1 is active.
  2. the shared "active" counter never exceeds 1 concurrently across the two
     runs' work functions (no overlapping execution windows).
  3. run 2's StartedAt timestamp is not before run 1's EndedAt timestamp.

A companion test, TestRunManager_DifferentRepposRunConcurrently, asserts the
inverse: two runs against two *different* repo identifiers ARE allowed to
run concurrently - the serialization bound is per gate repo, not global.

=== RESULT ===
PASS: run 2 was queued (not started, not rejected) while run 1 was active,
the two runs' execution windows never overlapped, and run 2 started only
after run 1 ended. Runs against different gate repos ran concurrently,
confirming the serialization bound is per-repo, not global. All of Task 5's
pre-existing lock/lifecycle tests continue to pass alongside these new ones.
