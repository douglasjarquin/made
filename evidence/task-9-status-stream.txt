=== QA Scenario (Task 9): Status stream completeness ===

TestRunManager_StatusStreamCompleteness subscribes to a run's events via
RunManager.Subscribe(id) BEFORE that run is ever Submit()-ted (the run ID is
generated up front via NewRunID(), then Subscribe is called, then Submit is
called - this ordering is what guarantees no race between subscribing and
the run manager's internal goroutine publishing its first event). The fake
work function then emits a 3-stage sequence (intent, rebase, build), each
with a started/finished pair. The test asserts the subscriber channel
delivers, in exact order and with nothing dropped:

  run_started
  stage_started(intent) -> stage_finished(intent)
  stage_started(rebase) -> stage_finished(rebase)
  stage_started(build)  -> stage_finished(build)
  run_completed

... and that no extra/duplicate event follows.

A companion test, TestRunManager_FailedWorkEmitsRunFailed, confirms the
terminal event is run_failed (carrying the returned error) when the work
function returns an error instead of nil.

Mailbox-level tests (mailbox_test.go) additionally cover: in-order delivery
to a single subscriber, per-run-ID isolation (a subscriber to run-1 never
sees run-2's events), fan-out to multiple simultaneous subscribers of the
same run, no delivery after Unsubscribe, and that Publish drops rather than
blocks once a subscriber's buffer is exhausted (verifying the bounded,
non-blocking overflow path without needing to actually exhaust it under
normal load, since mailboxBufferSize=256 is far larger than any real run's
event count).
